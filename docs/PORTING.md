# Porting Monaco to C#

LoomEditor ports `microsoft/vscode` → `src/vs/editor` (MIT license). This page explains **how** to port a file,
and keeps the **map** from Monaco files to LoomEditor files.

## Reference commit

All ports currently target **`0c9c0a4295a9222e12a605537738719455ae3056`** (vscode `main`, 2026-10-13).
When you port a file, read it at that commit:
`https://github.com/microsoft/vscode/blob/0c9c0a4295a9222e12a605537738719455ae3056/<path>`.
If you deliberately port from a newer commit, write that commit in the file header.

## Method, step by step

1. **Read the Monaco file and its tests first.** Tests are in `src/vs/editor/test/...` with the same path.
2. **Create the C# file in the matching LoomEditor folder** (see the map below) with this header:
   ```csharp
   // Ported from microsoft/vscode: src/vs/editor/common/core/range.ts
   // Upstream commit: <sha>  —  Copyright (c) Microsoft Corporation. MIT License.
   ```
   Use `// Inspired by microsoft/vscode: ...` when the design is adapted rather than translated.
   (`ConventionTests.PortedFiles_StateTheUpstreamCommit` checks the header.)
3. **Port the tests first, then the code.** Keep each Monaco test name in a comment:
   ```csharp
   // Monaco: 'swap start and stop'
   [Fact]
   public void Constructor_EndLineBeforeStartLine_SwapsPositions() { ... }
   ```
4. **Keep Monaco's concepts and behavior; use C# conventions.**

   | TypeScript (Monaco) | C# (LoomEditor) |
   |---|---|
   | `class Position { constructor(public readonly lineNumber, ...) }` | `readonly record struct Position` with properties |
   | `range.containsPosition(p)` | `range.Contains(p)` (Monaco name in `<remarks>`) |
   | `static Range.plusRange(a, b)` | instance method `a.Plus(b)` when it reads better |
   | `IDisposable`, `Disposable`, `DisposableStore` | `IDisposable`, `List<IDisposable>` |
   | `Emitter<T>` / `onDidChange` | .NET `event EventHandler<T>? Changed` |
   | `number` used as an int | `int` (check for overflow: JS numbers are 53-bit) |
   | `string.charCodeAt(i)` | `string[i]` (UTF-16 code unit — identical semantics) |
   | `Uint32Array`, typed arrays | `int[]`, `List<int>`, `Span<int>` |
   | `undefined` / `null` | nullable (`T?`) — enable nullable reasoning, don't use `!` to silence it |
   | regular expressions | `[GeneratedRegex]` (never `new Regex(...)` in hot paths) |
5. **Don't port what .NET already has** (`strings.ts` helpers, `arrays.ts`…): use the BCL, and say so in a comment.
6. **Don't optimize while porting.** First a faithful port with green tests; then benchmarks; then optimizations,
   each with a comment explaining *why* and the benchmark that proves it.
7. **Update the map below** in the same pull request.

## Behavior differences we accept

Any deliberate difference from Monaco must be documented in the XML doc of the member *and* listed here.

| Where | Difference | Why |
|---|---|---|
| Injected text `WidthInEm` (P6-25) | A `WidthOnly` inline decoration (injected text with empty content and `WidthInEm`) is not drawn and reserves no space in the drawn layout; the line breaker still counts its width | DirectWrite has no inline-block element |
| `MonospaceLineBreaksComputer` (P6-12) | `CreateLineBreaksFromPreviousLineBreaks` returns a new `ModelLineProjectionData` instead of updating the previous one in place, and uses local lists instead of the module-level `arrPool1` / `arrPool2` | `ModelLineProjectionData` is immutable; no shared mutable static state |
| `TextViewRenderer` hit test (P5-91) | The after-content text (the `⋯` of a folded line) is hit-tested as part of the line: its width counts in `GetLineWidth` and a click in it is `ContentText` at the max column | Monaco's DOM holds the `::after` content inside the line |
| `Position`, `Range`, `Selection` constructors | Throw `ArgumentOutOfRangeException` for values < 1 (Monaco accepts anything) | Fail fast; Monaco's own model validates positions anyway |
| Folding update delay (P5-88) | Fixed: 300 ms for the first computation, then 200 ms (Monaco measures the compute time and adapts the delay, clamped to 200…40 000 ms) | LoomEditor does not measure time; the provider is synchronous |
| `ViewModel.SetHiddenAreas` (P5-81) | `StableViewport` has no `_viewportStart` tracker: it takes the first view line of the layout viewport (when `scrollTop > 0`) and the delta to its offset | The tracker (`ViewModel` `_viewportStart`) is not ported |
| `ViewModel` model changes (P5-81) | When the lines reveal a view line because every line was hidden (`ViewModelLinesFromProjectedModel.AcceptVersionId` returns true), the layout is flushed | Monaco's layout copes with a line count of 0; `Range` cannot hold line 0 |

## Done in phase 5 (features)

The step-by-step cards are in **[docs/tasks/phase-5/](tasks/phase-5/)** (P5-01 … P5-96); the design is
[ADR 0009](adr/0009-editor-features.md). Main design decisions:

- A **feature** is one folder in `LoomEditor.View/Features/<Name>/` with a README, listed once in `EditorFeatures.cs`
  (Find, Folding, BracketMatching, Comment, Indentation, LinesOperations, WordHighlighter, MultiCursor, and the phase 3
  ones). `Scheduling` is infrastructure (`IEditorContext.Scheduler`), not a feature.
- Features delay work with `IEditorScheduler` (`RunOnceScheduler`, `Delayer`), never with timers of their own.
- **Model decorations** are ported (`DeltaDecorations`, `EditorDecorationsCollection`, change events, on the interval
  tree of phase 3); `DecorationStyles` replaces the CSS of Monaco and the renderer draws backgrounds, borders, inline
  styles, gutter icons and after-content text.
- The **language configuration** of Monaco is ported with the ten bundled `language-configuration.json` files; it drives
  auto-closing, surround, electric characters, on-enter rules, auto-indentation, comments and brackets.
- **Bracket pairs**: the bracket pair tree (parser, tokenizers, edit mapping) and the legacy matcher, behind one text
  model part used by matching and colorization.
- **Find / replace**: `TextModelSearch`, `FindModel`, `FindController`, `ReplacePattern` and a XAML find widget;
  Find-based multi-cursor.
- **Folding** and **hidden areas**: the view model has view lines (`ViewModelLinesFromProjectedModel`, the real
  `CoordinatesConverter`); the renderer, the hit testing and the control draw view lines. This is the base of word wrap.
- **Word highlight** with the textual provider only (semantic highlights are phase 8).
- JavaScript-only regex syntax is not supported (ADR 0009, decision 6).
- Every deliberate difference of phase 5 is a row of "Behavior differences we accept" (search for `(P5-`).
- The "done when" criterion (each feature is one documented folder) is met, 2026-10-22. The manual checks of P5-72 … P5-74,
  P5-90, P5-91 and P5-95 are for the maintainer.

## Done in phase 4 (TextMate grammars and themes)

The step-by-step cards are in **[docs/tasks/phase-4/](tasks/phase-4/)** (P4-01 … P4-50); the design is
[ADR 0007](adr/0007-textmate-regex-engine.md) (regex engine) and [ADR 0008](adr/0008-syntax-highlighting.md). Main
design decisions:

- Three upstream repositories are ported: `microsoft/vscode` (Monaco's token model and the workbench's TextMate
  service), `microsoft/vscode-textmate` v9.3.2 and `microsoft/vscode-oniguruma` v1.7.0 (headers name the repository).
  The map above is complete for all three.
- Regexes run on a **native Oniguruma 6.9.10** (`onig.dll`, built by `src/native/oniguruma/build.ps1`), through
  `IOnigLib`; patterns and subjects are UTF-16.
- Grammars are read with `System.Text.Json.Nodes` (no serializer, Native AOT); loading is synchronous.
- Monaco's token store, state store and `AttachedViews` live in `LoomEditor.Core`; the tokenization registry is an
  instance per editor, not a global.
- One **background thread** per editor tokenizes the whole file (`TextMateWorkerTokenizer`) and publishes its results on
  the UI thread; the UI thread only tokenizes the visible lines it does not know yet, with Monaco's heuristics.
- Themes are VS Code `.json` themes (Dark Modern and Light Modern among the ten built in); `ThemeToTextMate` gives
  the grammars their token rules and the registry its color map. The control has `LanguageId` and `Theme`.
- The "done when" criterion is met: the golden tests (`tests/LoomEditor.TextMate.Tests/Golden`) compare the scopes and
  the Dark Modern / Light Modern colors of ten languages (C#, TypeScript, JavaScript, JSON, HTML, CSS, XML, Markdown,
  Python, YAML) with files produced by the real vscode-textmate (`eng/golden`), 2026-10-20: 30 tests, all green.
  One deliberate change was needed: the YAML grammars (see "Behavior differences").
- Reference numbers (grammar speed, 60 visible lines in a 100 000-line file, whole-file worker run) are in
  `docs/performance.md`. The viewport case (8.1 ms) is just over the 8 ms limit of card P4-49: follow-up card proposed.

## Done in phase 3 (editing)

The step-by-step cards are in **[docs/tasks/phase-3/](tasks/phase-3/)** (P3-01 … P3-55); the design is
[ADR 0006](adr/0006-editing-and-text-input.md). Main design decisions:

- Monaco's cursor (`editor/common/cursor/*`) is ported into `LoomEditor.View/Cursors/` as is: `CursorsController`,

- Commands and keybindings: Monaco's core commands and VS Code's default Windows shortcuts; `when` clauses are C# predicates.

  Gallery (`docs/testing/phase-3-manual-tests.md`, 2026-10-19). Not tested: Korean IME and Windows 10.

## Done in phase 2 (rendering)

The step-by-step cards are in **[docs/tasks/phase-2/](tasks/phase-2/)** (P2-01 … P2-23); the design is
[ADR 0005](adr/0005-viewport-rendering.md). Main design decisions:

- Scrolling and layout are Monaco's, ported to `LoomEditor.View/Layout/` with integer arithmetic (`Scrollable`,
  `LinesLayout`, `ViewLayout`, `ViewModel` subset), so a 100 MB document keeps exact offsets (`bigNumbersDelta`).
- The control draws only the visible lines on a viewport-sized `CanvasControl`: no `CanvasVirtualControl`, no
  `ScrollViewer`. Scrollbars are XAML `ScrollBar` primitives mirroring the `Scrollable`.
- Text is measured and laid out by DirectWrite through `Win2DTextMeasurer`; tabs are DirectWrite tab stops, so
  proportional fonts, wide characters and emoji need no special case. Line layouts are cached by text.
- The caret blinking state machine (`CursorBlinking`) has no timer; the control drives it with a `DispatcherQueueTimer`.
- Font, tab size and DPI changes go through one method, `RecreateTextMeasurer`.
- The "done when" criterion is met: the Gallery scroll test on a 100 MB document, in a Native AOT build, runs at
  60 fps with p95 17 ms (`docs/performance.md`, "Scrolling (card P2-22)").

## Done in phase 1 (piece tree and text model)

The step-by-step cards are in **[docs/tasks/](tasks/README.md)** (P1-01 … P1-32). Main design decisions:

- `PieceTreeBase` is split into `partial` files by concern (`.Lines`, `.Positions`, `.Insert`, `.Delete`, `.Crlf`,
  `.Snapshot`, `.Eol`) and **owns** a `RedBlackTree` (composition) instead of mixing tree and text code.
- **One sentinel node per tree** instead of Monaco's global mutable `SENTINEL` (thread safety, parallel tests).
- `StringBuffer` is a growable `char[]`, not a `string` (appending to the change buffer must not be quadratic).
- `PieceTreeTextBuffer` / `ITextBuffer` stay `internal`; the public API is `TextModel`, which uses `TextEdit` for edits.
- Decorations and injected text were deferred to phase 2+ (search in the piece tree: P5-64).
- Monaco's workspace-wide `IUndoRedoService` is replaced by a per-model `UndoRedoStack`.
