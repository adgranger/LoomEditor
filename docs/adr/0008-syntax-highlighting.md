# ADR 0008 — Syntax highlighting: vscode-textmate, Monaco's tokens, a background tokenizer thread, VS Code themes

- **Status:** accepted
- **Date:** 2026-10-19

## Context

Phase 4 colors the text like VS Code does. In VS Code this involves four code bases:

1. **vscode-textmate** (separate repository): loads TextMate grammars and turns a line + a state into tokens
   (scopes, or 32-bit metadata with the colors of a theme).
2. **vscode-oniguruma**: the regex engine (ADR 0007).
3. **Monaco** (`src/vs/editor`): the token types (`encodedTokenAttributes.ts`, `tokens/*`), the per-line state store
   and the tokenization of the text model (`model/textModelTokens.ts`, `model/tokens/*`), and how tokens reach the view.
4. **The VS Code workbench** (`src/vs/workbench/services/textMate/`, `…/themes/`): the grammar registry, the adapter
   from a grammar to Monaco's `ITokenizationSupport`, the **background worker** that tokenizes the whole file, and theme
   loading.

The architecture (rule 9) says: the model changes on the UI thread only; tokenization runs in the background,
incrementally and cancellably, and publishes its results on the UI thread. The maintainer confirmed on 2026-10-19:
a real background thread (like VS Code's worker), golden tests generated by the real vscode-textmate, and ten languages:
C#, TypeScript, JavaScript, JSON, HTML, CSS, XML, Markdown, Python, YAML.

## Decisions

1. **Pinned upstream commits.**
   - `microsoft/vscode` `0c9c0a4295a9222e12a605537738719455ae3056` (as in phases 1–3).
   - `microsoft/vscode-textmate` **v9.3.2** = `25b68dad91920b1ed79d357534b8c4582f62d80d` (the version VS Code uses at
     the commit above: `package.json` `^9.3.2`, lock file 9.3.2).
   - `microsoft/vscode-oniguruma` **v1.7.0** = `716aeaa229e4ae2e3b0057377b55743e9a3e995b`.
   Ported file headers name the repository: `// Ported from microsoft/vscode-textmate: src/rule.ts` (the convention
   test accepts the three repositories, P4-03).
2. **Where things go.**

   | Upstream | LoomEditor |
   |---|---|
   | vscode-oniguruma, vscode-textmate `onigLib.ts` | `LoomEditor.TextMate/Oniguruma/` |
   | vscode-textmate (`rule`, `grammar/*`, `matcher`, `utils`, `registry`, `main`, `encodedTokenAttributes`, `diffStateStacks`) | `LoomEditor.TextMate/Grammar/` |
   | vscode-textmate `theme.ts` (the scope → style trie used by grammars) | `LoomEditor.TextMate/Theme/` |
   | vscode-textmate `rawGrammar.ts`, `parseRawGrammar.ts`, `plist.ts` | `LoomEditor.TextMate/Parsing/` |
   | workbench `textMate/common/*`, `tokenizationSupport/*`, `backgroundTokenization/*` | `LoomEditor.TextMate/Tokenization/` |
   | grammar files of the ten languages | `LoomEditor.TextMate/Grammars/<language>/` (embedded resources) |
   | Monaco `encodedTokenAttributes.ts`, token types of `languages.ts`, `nullTokenize.ts`, `tokenizationRegistry.ts`, `LanguageIdCodec`, `tokens/*` | `LoomEditor.Core/Tokens/` |
   | Monaco `model/textModelTokens.ts`, `fixedArray.ts`, `mirrorTextModel.ts`, `model/tokens/*` (subset) | `LoomEditor.Core/Model/Tokens/` and `TextModel.Tokenization.cs` |
   | workbench `themes/common/colorThemeData.ts` (subset), `themeCompatibility.ts`, default colors of `editorColors.ts` / `editorColorRegistry.ts` | `LoomEditor.Themes/` |
   | `extensions/theme-defaults/themes/*.json` | `LoomEditor.Themes/BuiltIn/` (embedded resources) |
   | gluing grammars, model, theme and worker for one editor | `LoomEditor.View/Highlighting/` |

   The dependency table of `ARCHITECTURE.md` does not change: TextMate and Themes know only Core; View joins them.
3. **vscode-textmate is ported faithfully, with three deliberate changes** (listed in `docs/PORTING.md`):
   - **Synchronous loading.** `Registry.loadGrammar` returns the grammar, not a `Promise`; the `loadGrammar` option is a
     `Func<string, RawGrammar?>`. Grammars are embedded resources, so there is nothing to wait for.
   - **No font attributes.** The 9.3 font feature (`fontFamily`, `fontSize`, `lineHeight` in theme rules, `FontAttribute`,
     `FontInfo`, `LineFonts`, `IFontInfo`) is not ported. Theme rules keep foreground, background and font style.
     The tests `'Fonts are correctly set'` and `'… 2'` are not ported.
   - **JSON is read with `System.Text.Json`** (`JsonDocument`, comments and trailing commas allowed), not with the
     ported `json.ts`. The location metadata (`$vscodeTextmateLocation`) is not produced; `json.test.ts` is not
     ported. `plist.ts` **is** ported (the JavaScript regex grammar of VS Code and some test fixtures are plists).
4. **Monaco's token model goes to Core.** `TextModel` gets Monaco's tokenization part (subset): a language id,
   `GetLineTokens`, `ForceTokenization`, `HasAccurateTokensForLine`, the `TokensChanged` event, the background
   tokenization state, and the attached-view mechanism (`SetVisibleLines`) that tokenizes the viewport first. The
   tokenization registry is an **instance**, not Monaco's global singleton (CLAUDE.md: no global mutable state): each
   editor gives its registry to the model it creates. Not ported: semantic tokens (`sparse*`), tree-sitter, font tokens,
   bracket pairs, Monarch, and Monaco's `TokenTheme` (`languages/supports/tokenization.ts`, used only by Monarch).
5. **Threading (VS Code's worker, as a thread).**
   - The UI thread owns the `TextModel`, its token store and its state store. It tokenizes **only what is visible and
     not yet known**, with Monaco's heuristics (`TokenizerWithStateStoreAndTextModel.tokenizeHeuristically`).
   - Each editor with a TextMate language has **one background thread** (`IsBackground = true`,
     `ThreadPriority.BelowNormal`) that runs the port of `textMateWorkerTokenizer.ts`: a `MirrorTextModel` of the
     document, its own state store, batches of at most 200 lines, slices of 20 ms.
   - UI → worker messages go through a `System.Threading.Channels` channel, in order: new model, content changes
     (copies of `ModelContentChangedEventArgs`), language change, retokenize, theme, dispose. Worker → UI results are
     posted with an **`IUiDispatcher`** (`LoomEditor.Core/Threading/`, a one-method "post to the owner thread"
     interface, so that `LoomEditor.TextMate` can use it): the control implements it with `DispatcherQueue`, tests with
     a manual queue.
   - Results are **objects, not bytes**: tokens travel as `ContiguousMultilineTokens`, states as references to
     immutable vscode-textmate `StateStack`s. `diffStateStacks.ts` is ported (its round trip is part of the vscode-textmate
     tests) but not used on the wire. The UI side is the port of `textMateWorkerTokenizerController.ts`: it drops stale
     results and rebases the others on the edits made since (`MonotonousIndexTransformer`, `LengthEdit`).
   - **Grammars are not thread-safe** (rule caches, scanners, theme match cache). Each thread has its own registry and
     grammars, created from the same **read-only** raw grammars. A native scanner is used and freed only by the thread
     that created it.
   - Limits are VS Code's: no tokenization for models above 20 MB or 300 000 lines (`isTooLargeForTokenization`), plain
     tokens for lines of 20 000 characters or more (`maxTokenizationLineLength`), 500 ms per line
     (`tokenizeLine2(…, 500)`, the start state is kept when it stops early).
   - Without a background tokenizer (unit tests, a plain `ITokenizationSupport`), the model uses Monaco's
     `DefaultBackgroundTokenizer` driven by an `ITokenizationScheduler` (idle callbacks in Monaco).
6. **Grammars and languages.** Each language has a folder `LoomEditor.TextMate/Grammars/<language>/` with the grammar
   file(s), copied verbatim from `extensions/<language>/syntaxes/` at the pinned VS Code commit, and a `language.json`:
   `id`, `aliases`, `extensions`, `filenames`, `scopeName`, `path`, `embeddedLanguages`, `tokenTypes`, `injectTo`,
   `balancedBracketScopes`, `unbalancedBracketScopes` (the fields of VS Code's grammar and language contributions).
   The list of built-in languages is one file (`BuiltInLanguages.cs`). Grammars needed by another grammar (JavaScript
   regex, Python regex, the six YAML files, HTML derivative, the JSDoc injections) are bundled too. Language configuration
   (brackets, comments, auto-closing) is **phase 5**.
7. **Resources.** Grammars and themes are **embedded resources** with an explicit `LogicalName`, read with
   `Assembly.GetManifestResourceStream`. ADR 0001 saw embedded resources fail in the AOT Gallery once, without
   investigation: card P4-01 checks it first and writes the result here. If they cannot work under Native AOT, P4-01
   stops and proposes the fallback (the build generates `ReadOnlySpan<byte>` UTF-8 literals).

   **Findings of the AOT spike (P4-01, 2026-10-19).** A throw-away probe in `LoomEditor.TextMate`, called by the
   Gallery when `LOOM_PROBE` is set, was published with `dotnet publish samples/LoomEditor.Gallery -c Release -r win-x64`
   and run; it was also run with `dotnet run` (JIT). Same results in both:
   - **Embedded resources work under Native AOT.** `GetManifestResourceStream("LoomEditor.TextMate.Probe.probe.json")`
     returned the stream (22 bytes) and `GetManifestResourceNames()` listed it. The only MSBuild item needed is
     `<EmbeddedResource Include="…" LogicalName="…" />` in the library; the ILC keeps manifest resources by default
     (no `IlcKeepManifestResources`-like property exists in `Microsoft.DotNet.ILCompiler` 11.0 rc, and none is
     needed). The fallback (UTF-8 literals) is **not** needed. The cause of ADR 0001's known issue 2 was not
     reproduced (most likely a resource name that did not match: without `LogicalName` the name depends on the
     folder and root namespace), so every resource gets an explicit `LogicalName`.
   - **`onig.dll` ships and loads.** With `<None Include="…/artifacts/native/win-x64/onig.dll" Pack="true"
     PackagePath="runtimes/win-x64/native" CopyToOutputDirectory="PreserveNewest" />` in `LoomEditor.TextMate`, the
     DLL is copied to the Gallery's publish folder; `NativeLibrary.TryLoad("onig.dll", assembly, null, out _)`
     returns `true` and `onig_version()` (through `[LibraryImport("onig")]`) returns `6.9.10`. `[LibraryImport]`
     needs `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>` in the project (SYSLIB1062 otherwise).
   - **Publish warnings: 0.**
   - **SDK 11.0.100 rc.2 breaks the AOT publish of the Gallery** (seen during the spike; `global.json` pins rc.1, which
     was not installed, so the SDK rolled forward). rc.2 adds an "optimized" Native AOT publish
     (`_PublishOptimizedBuildAlternative`) that runs `PrepareResources` before `ResolveReferences`: the WinUI XAML
     compiler gets no references and fails with `WMC1007: Cannot resolve metadata for WinUI types`. Workaround:
     `-p:UseOptimizedPublish=false` (or install SDK rc.1).
     **Resolved:** the Gallery sets `<UseOptimizedPublish>false</UseOptimizedPublish>`, and `global.json` now pins rc.2.
     (With the optimized publish, even once WMC1007 is bypassed, the exe crashes at startup with
     `FileNotFoundException: WinRT.Runtime` in the generated `GlobalVtableLookup` module initializer.)
8. **Themes.** `LoomEditor.Themes` loads VS Code color themes (`.json`, with comments): `include` (parent first),
   `colors` (with `"default"` removing an inherited color), `tokenColors` as an inline array, and the old JSON form
   with a `settings` array (`themeCompatibility.ts`). `tokenColors` given as a path, and `.tmTheme` files, are **not**
   supported: VS Code reads both with its plist parser (`_loadSyntaxTokens`), which lives in `LoomEditor.TextMate`
   (that is a dependency Themes may not have). The ten default themes use neither.
   `EditorTheme` gets the token rules, the theme type (dark, light, high-contrast dark, high-contrast light) and the
   editor colors resolved with VS Code's defaults. The built-in themes are the ten `theme-defaults` files;
   **`EditorTheme.Dark` and `EditorTheme.Light` become Dark Modern and Light Modern**, loaded from them.
   The color map follows VS Code (`TokenColorIndex`, rule 0 = default foreground and background, `normalizeColor`).
9. **Drawing.** The view model gives the renderer the inflated tokens of each visible line. The renderer gives
   DirectWrite one color per token range (`CanvasTextLayout.SetColor`) and the font style (italic, bold, underline,
   strikethrough). The line layout cache is keyed by the text **and** the style bits of the tokens (foreground + font
   style), so a recolored line gets a new layout and an unchanged line keeps its own.
10. **Public API (phase 4).** `LoomEditor.Language` (string language id, dependency property, default `"plaintext"`),
    `LoomEditor.Theme` (`EditorTheme`, dependency property, default `EditorTheme.Dark`), `EditorTheme.Load` (a VS Code
    theme from JSON text, with a callback that reads included files), `EditorTheme.BuiltIn` (the ten default themes),
    and the list of built-in language ids. Grammars supplied by the host application are **not** part of phase 4.
11. **Golden tests.** `eng/golden/` holds a Node script with **pinned** `vscode-textmate` 9.3.2 and `vscode-oniguruma`
    1.7.0 (lock file committed). It loads **our** grammar and theme files, tokenizes each sample, and writes the expected
    scopes and colors (Dark Modern and Light Modern). The samples are the `extensions/vscode-colorize-tests` fixtures of
    the ten languages (MIT). The C# golden test compares our output with these files. Node is needed only to regenerate
    them, never to build or test.
12. **Out of phase 4:** semantic highlighting, tree-sitter, bracket pair colorization, language configuration and
    everything that uses it (phase 5), the token inspector, host-supplied grammars, `.tmTheme` themes, font tokens.

## Consequences

- The same grammar, theme and text give the same colors as VS Code; the golden tests prove it for ten languages.
- Each editor costs one background thread and two copies of its grammars (UI thread and worker).
- Scrolling stays smooth on big files: the viewport is tokenized first on the UI thread; the rest arrives from the
  worker in batches.
- Phase 5 (brackets, auto-indent, comments) can read tokens (`StandardTokenType`, language id per token) from the model.
